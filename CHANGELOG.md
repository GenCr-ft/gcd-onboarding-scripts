### Changed

- The traceability gate in the generated pre-commit wrapper no longer changes its answer with the shell's `PATH`, and no longer reports a crash as a validation failure. Step 1 executed the linter as a bare executable, so the interpreter came from `#!/usr/bin/env python3`; on the dev machine `/home/lgan/.gft-studio/.poetry/bin/python3` (no PyYAML) resolves **before** `/usr/bin/python3` (PyYAML 6.0.3), so the same commit passed one hour and was hard-blocked the next, told `Planning metadata validation failed` — sending the author hunting frontmatter for a problem that did not exist. **The two reported defects are one defect**: a `ModuleNotFoundError` crash and a genuine violation *both* exit `1`, so "could not run" cannot be recovered from the linter's status after the fact and must be established before invocation — which makes the proposal of detecting a crash by its exit signature unimplementable. **The pin already existed and was simply not being called**: `gcd-ops-scripts` declares `PyYAML >= 6.0.2` and ships a `validate-planning-metadata` console script whose shebang is an *absolute* interpreter path into the environment that declares it, verified running with `PATH=/nonexistent`. The wrapper reached past it to exec the raw source file, re-acquiring the `PATH` dependency packaging had already removed. The generator now bakes that entry point, resolved **from `target_dir` only, never `command -v`** — an earlier revision accepted `command -v` and was wrong twice over: it re-introduced ambient resolution through another variable, and let source and execution disagree, since `linter_src` comes from `target_dir` while a global hit could be a different revision entirely. It was caught by the fixture arms *finding the developer's real linter on `PATH` and running it against a mock workspace*. Where no entry point is installed, candidate interpreters are **probed** for the requirement before use — never a bare `python3`, which is the defect itself — and if none satisfies it the gate **fails closed** with a distinct exit code `3` and a message naming the requirement, the interpreters tried and the fix, explicitly not the words "validation failed". Deliberately **not** done: changing the linter's own shebang, since `#!/usr/bin/env python3` is correct for a source module in a package and an absolute path there would break the repo's own venv, its CI and macOS — a shebang cannot express "the interpreter that has my dependencies", which is precisely what an entry point is for. `WRAPPER_VERSION` 2 → 3 is mandatory rather than cosmetic: the skip branch matches on the version string, so without it every clone stays on v2 — the exact failure WI-268 Stage A existed to repair, one version later. Also fixed in passing: the requirement override is read at **generation** time, not at source time, because this include is sourced once at startup and resolving it there silently ignored any later change. Six arms assert executed **behaviour**, never the generated file's text, since a text match can fail a correct fix or pass on a comment; the `PATH`-independence arm carries an explicit non-empty guard so two silent runs cannot compare equal and pass vacuously. Scoped honestly: this makes *interpreter* resolution `PATH`-independent — the same gate's residual `git`-on-`PATH` dependency, where the linter substitutes the branch name `"main"` and reports a real violation as `✓ Planning metadata is fully compliant.`, is GenCr-ft/gcd-ops-scripts#189 and is not claimed here. Supersedes #271, which reported the same defect first. (#272, @loigallain)
- The generated pre-commit wrapper no longer **fails open**, the `commit-msg` stage is installed, and its marker is **versioned** so an old wrapper is upgraded instead of skipped. Measured across the 34 workspace clones before the change: **34/34** declared a hook set, **30/34** carried the wrapper with no `pre-commit.legacy` beside it and therefore reached a bare `exit 0`, **0/34** had a `commit-msg` hook, and **33/34** declared hooks that nothing ran — three secret scanners among them. The wrapper's presence turned out to be *anti-correlated* with hooks working: the single clone whose declared set ran is `gencr-ft.github.io`, and it ran **because** `pre-commit install` displaced the wrapper into `.legacy`. The wrapper is now graduated rather than binary — delegate to a legacy hook that is not itself; else run the declared set directly; else, if a config is declared but `pre-commit` is absent, **fail closed** naming the binary, because a developer with a broken toolchain must not get the same green as one with a working install; else exit 0, since nothing is declared. A **self-call guard** refuses a delegate carrying the wrapper's own marker: the delegate path is baked in at generation time and `pre-commit install --hook-type pre-commit` *moves* an existing hook there, so after that the delegate **is** the wrapper and delegating recurses without bound — previously measured at 7 levels, now reproduced in a test that returns `exit 124` under `timeout`, from the precondition observed live in `gencr-ft.github.io`. Only `--hook-type commit-msg` is installed, never the pre-commit type, and the test asserts the **requested hook type** rather than just the resulting file, because which type is requested is what creates or avoids that loop. **The versioned marker had to land in the same change**: the old skip branch matched a version-less marker, so the exact population needing repair was the population it skipped, which is why re-running onboarding had never fixed anything. Proven by the Stage A exit criterion, with the pre-change generator extracted from `origin/main` rather than reconstructed — it exits 0 and reports `wrapper(s) installed, 0 skipped, 0 failed` while writing no `commit-msg`, exiting 0 against a *failing* declared set, never invoking that set, and producing a byte-identical wrapper on a second run. **Three test arms were wrong before the code was, and each failure read as an implementation defect**: the first asserted on *text*, grepping for a bare `exit 0` that the correct v2 wrapper also contains for the no-config case, so a static match would have failed a working fix; the fixture faked the repository with `mkdir -p \.git/hooks`, which `pre-commit install` refuses outright; and the real `pre-commit` **cannot run under a hermetic `HOME` at all** — shebang `/usr/bin/python3`, module under `~/.local/lib` — so every test in this repo would get `ModuleNotFoundError`, replaced with an argv-recording stub. Also dropped from scope after measurement refuted the claim justifying it: a dispatch entry point is **not** required for testability, because this repo's tests source the includes and call functions directly, and a nonexistent function exits **127** loudly rather than 0 silently. Stage A only — the 34-clone sweep is a separate change, and it should expect a wave of first-time findings, since 33 clones will run `shellcheck`, `markdownlint` and `detect-secrets` for the first time. (#268, @loigallain)
